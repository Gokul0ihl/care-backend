Limits of the existing APIs

What still cannot be done, or only with a workaround, when no backend code is changed.

  • Not possible Avg Waiting Time: emr_token stores no called or served time, and no API reports durations.
  • Workaround Register & Print is 3 calls, not one transaction. The patient is created first because the other calls need its id, and a batch request cannot pass one call's result to the next. If call 2 or 3 fails, retry it; if it keeps failing, set the encounter status to entered_in_error.
  • Workaround MLC and UHID numbers are generated by the frontend. Two receptionists saving at the same moment can pick the same number. The UHID config's unique rule rejects a duplicate so the frontend can retry; the MLC number in external_identifier has no such check.
  • Workaround "vs last month" percentages need two count calls per card. Date filters are confirmed for encounters (created_date_after/before) and appointments (date_after/before); a created-date filter on the patient list is not confirmed.
  • Workaround Emergency-only Active Cases: an encounter_class filter was not seen in the frontend; filter by priority=emergency or the triage tag instead, and confirm in the backend.
  • Workaround Questionnaire answers are not searchable columns. They are fine for display and printing, but you cannot list patients by police station or accompanying person through the API.
  • Workaround Unknown patients are saved with a placeholder name such as "Unknown Male" and empty addresses. Update them later with PUT /api/v1/patient/{id}/ once identified.
API routes and request types come from the frontend src/types/**/*Api.ts files; tables were checked in the local care database. Replace {facilityId} and other ids with real values. Items marked "not confirmed" need a check in the backend source.
